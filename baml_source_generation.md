## How generated BAML uses the handwritten BAML

The handwritten file is:

`examples/agents/meteo-agent/baml_src/meteo_agent_prompt.baml`

It defines:

```baml
function ChooseMeteoAgentAction(user_message: string) -> DevMeteoToolSessionPlan
```

`DevMeteoToolSessionPlan` is **not handwritten**. It comes from generated `_baml_runtime.baml`.

Generation flow:

1. Builder reads `manifest.json`, sees tool:

   ```json
   "tools": ["dev/meteo-tool"]
   ```

2. Builder generates tool/session types into:

   ```text
   examples/agents/meteo-agent/baml_src/_baml_runtime.baml
   ```

   This includes:

   - `DevMeteoToolInput`
   - `DevMeteoToolOutput`
   - `DevMeteoToolOpenStep`
   - `DevMeteoToolSendStep`
   - `DevMeteoToolSearchReadStep`
   - `DevMeteoToolPageReadStep`
   - `DevMeteoToolFinishStep`
   - `DevMeteoToolAbortStep`
   - `DevMeteoToolSessionStep`
   - `DevMeteoToolSessionPlan`

3. The handwritten function returns that generated type:

   ```baml
   -> DevMeteoToolSessionPlan
   ```

4. Builder does a first BAML compile with:

   - handwritten `meteo_agent_prompt.baml`
   - generated tool prelude `_baml_runtime.baml`

5. From the compiled IR, builder detects that `ChooseMeteoAgentAction` returns a `*SessionPlan`.

6. Then it generates narrowed per-phase functions back into `_baml_runtime.baml`:

   ```baml
   function ChooseMeteoAgentAction__select(...) -> DevMeteoToolOpenStep | DevMeteoToolSearchReadStep | DevMeteoToolPageReadStep
   function ChooseMeteoAgentAction__act__dev_meteo_tool(...) -> DevMeteoToolSendStep | DevMeteoToolSearchReadStep | DevMeteoToolPageReadStep | DevMeteoToolAbortStep
   function ChooseMeteoAgentAction__continue__dev_meteo_tool(...) -> DevMeteoToolSendStep | DevMeteoToolSearchReadStep | DevMeteoToolPageReadStep | DevMeteoToolFinishStep | DevMeteoToolAbortStep
   ```

7. Those generated functions **copy the handwritten prompt body verbatim** from `ChooseMeteoAgentAction`, but wrap it with phase-specific preambles/suffixes.

Example generated shape after the prompt-softening pass:

```baml
prompt #"[RUNTIME PHASE: SELECT] Entry decision before any tool session is bound.\n...
<handwritten prompt copied here>
PHASE CONSTRAINT (select): Emit exactly one JSON value matching this narrowed return schema. ...
"#
```

The generated wrapper is intended to describe mechanics only: phase facts, schema legality, and archive-ref syntax. Business behavior such as freshness, reuse thresholds, whether to paginate, and when to call a tool belongs in the handwritten prompt or explicit tool metadata.

So the dependency is two-way:

- handwritten BAML uses generated session-plan types;
- generated BAML uses the handwritten function’s IR prompt/client/args to emit phase-specific variants.

At runtime, `src/index.ts` calls:

```ts
await runGeneratedStepExecutor("ChooseMeteoAgentAction", {
  user_message: userText,
}, { max_steps: MAX_REACT_STEPS });
```

But the Rust step executor does **not** invoke the base function directly. It maps FSM state to generated phase functions:

- first hop → `ChooseMeteoAgentAction__select`
- after Open → `ChooseMeteoAgentAction__act__dev_meteo_tool`
- after Send/Read done → `ChooseMeteoAgentAction__continue__dev_meteo_tool`

Then `PresentMeteoAgentReply` synthesizes the user-facing answer.

## Hooks / phases

There are two related vocabularies.

### Generated function phase suffixes

From `crates/baml-rt-core/src/function_id.rs`:

- base/root: `ChooseMeteoAgentAction`
- select: `ChooseMeteoAgentAction__select`
- act: `ChooseMeteoAgentAction__act__{tool_slug}`
- consume: `ChooseMeteoAgentAction__consume__{tool_slug}` — **reserved, not emitted today**
- continue: `ChooseMeteoAgentAction__continue__{tool_slug}`

So if “hooks” means function phases:

```text
root/base
select
act
consume   reserved/future
continue
```

There is no generated `__open` hook. “Open” is the operation selected during the `__select` phase.

### FSM step ops

The generated step classes expose ops:

```text
Open
Send
SearchRead
PageRead
Finish
Abort
```

For meteo specifically:

- select phase can return `Open`, `SearchRead`, or `PageRead`
- act phase can return `Send`, `SearchRead`, `PageRead`, `Abort`
- continue phase can return `Send`, `SearchRead`, `PageRead`, `Finish`, `Abort`

## Prompt templates used/generated by builder

### Bootstrap templates

In `crates/baml-rt-builder/src/builder/bootstrap.rs`:

- `prompt_template_no_tools(...)`
- `prompt_template_with_tools(...)`
- `index_ts_template(...)`

These are only for creating a new agent skeleton. The meteo agent’s prompt appears custom/handwritten, not directly from the bootstrap template.

### Tool/interface prompt text

In:

```text
crates/baml-rt-builder/src/builder/baml_gen/prompt_copy.rs
crates/baml-rt-builder/src/builder/baml_gen/tool_interfaces.rs
```

Builder generates descriptions and session step classes into `_baml_runtime.baml`, including archive read guidance, citation rules, and step descriptions.

### Per-phase prompt generation

Current active code is:

```text
crates/baml-rt-builder/src/builder/baml_gen/session_from_ir/mod.rs
```

It does:

```rust
let prompt_template = &config.prompt_template;
```

Then emits phase functions by concatenating:

```text
phase preamble
+ handwritten IR prompt_template
+ phase constraint suffix
```

The active generated prompts now use runtime phase labels:

```text
[RUNTIME PHASE: SELECT]
[RUNTIME PHASE: ACT]
[RUNTIME PHASE: CONTINUE]
```

Important note: there is also:

```text
crates/baml-rt-builder/src/builder/baml_gen/session_from_ir/phase_prompt.rs
```

which defines a newer-looking prompt algebra with:

- `SESSION_STEP_STABLE_PREFIX_BAML`
- `Phase: SELECT`
- `Phase: ACT`
- `Phase: CONTINUE`
- footer listing narrowed union types
- stripping/re-appending `{{ ctx.output_format }}`

But it does **not** appear wired into `session_from_ir/mod.rs` via `mod phase_prompt;` or calls. The active output comes from the prompt builder in `mod.rs`, not from `phase_prompt.rs`.
