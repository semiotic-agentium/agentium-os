# Demo Plan: Agentium Observability Incident Copilot

## Goal

Demonstrate Agentium-OS as an agentic observability layer that reacts to real Grafana alerts from a live Kubernetes workload, investigates metrics plus lightweight log/trace evidence through approved tools, summarizes likely cause/impact, and stores an actionable report in the Agentium provenance trail for retrieval by `context_id`.

Core message:

> Agentium-OS connects to existing observability tooling, receives alert events, organizes specialist investigations, cites real evidence, and produces concise incident reports that operators can pull on demand and audit through the provenance graph.

## Demo Stack Decision

Keep the deployable demo small:

- **Grafana**
- **Prometheus**
- **Loki**
- **Agentium-OS runner + agents**
- **Dummy services + synthetic load (k6)**
- **Failure harness + ground-truth ledger**

No Tempo, Mimir, FireHydrant, PagerDuty, MS Teams, or generic webhook delivery. **Loki is in scope** for real log evidence. **Slack is in scope** via new `agents/slack-notify/` + new `support/slack_notify` write tool. The existing `agents/slack-agent/` is read-only and deferred for a future Slack-as-input / follow-up role; it is **not** the notifier.

Evidence types still include:

- **Metrics**: Prometheus queried through Grafana MCP.
- **Real structured logs**: JSON logs emitted by `checkout-api` / `payments-api` to stdout, shipped to Loki, and queried through Grafana/LogQL. App logs do **not** carry a demo-only `incident_id`; investigators correlate by service, alert time window, route/status fields, and message keywords.
- **Synthetic span-like records**: structured records generated by `checkout-api` and mirrored into Grafana annotations by the failure harness. Agents read via `mcp/grafana/get_annotations` filtered by `kind=trace`. Not real traces, not Tempo.

**Honest framing** (must appear in runbook and demo narration): log evidence is real Loki-backed structured application logs. Span/trace "evidence" is synthetic structured records mirrored into Grafana annotations, not a real trace backend. Operators see incident windows/spans in Grafana annotations and logs in Grafana Explore via Loki. Tempo is the obvious extension path.

**Report delivery is provenance-first.** LLM outputs land in Agentium provenance, so the canonical final report lives there, not in Grafana annotations or a separate incident service. Slack receives a summary + dashboard URL (pointer, not record). MS Teams / generic webhook are extension paths.

## Core Demo Shape

```txt
checkout-api + payments-api + k6 synthetic load
  -> real Prometheus metrics
  -> real structured logs generated by checkout-api/payments-api and shipped to Loki
  -> synthetic span evidence generated by checkout-api
  -> harness injects failure + writes ledger + Grafana annotations
       (incident window, kind=trace)
  -> Grafana alert fires -> grafana.alert.v1
  -> grafana-alerts tool (in-runner) webhook enqueues IngressItem
       and maps active alert fingerprint/groupKey to Agentium context_id
  -> GrafanaAlertEventProducer emits ProducedEvent (schema_version=grafana.alert.v1,
       source_kind=grafana, source_key=grafana:local, context_id + message_id)
  -> host subscription matching turns the ProducedEvent into an AgentDispatchRequest
       for every matching agent (coordinator only, for this demo)
  -> coordinator receives event in that context
  -> grafana investigator gathers metrics, Loki logs, and trace annotations
       (mcp/grafana/query_prometheus + LogQL/Loki query via Grafana + mcp/grafana/get_annotations for traces/windows)
  -> coordinator synthesizes final report with citations (no separate synthesizer agent)
  -> agents/slack-notify (new write-only agent) posts summary + dashboard URL
       to configured Slack channel via support/slack_notify tool
  -> final report is stored automatically as LLM output in provenance
  -> operator opens dashboard at ${AGENTIUM_UI_BASE_URL}/?view=dashboard&contextId={context_id}
  -> E2E eval asserts report evidence against ground-truth ledger
```

MCP alone is pull-only. It is good for enrichment after a trigger, but not ideal for alert ingestion. Grafana Alerting owns detection/delivery; Agentium owns investigation/orchestration/reporting.

## Runtime Lifecycle

This is a long-lived deployed system, not a one-shot CLI run. Every component below stays up across incidents.

- **Agentium runner**: deployed StatefulSet. Hosts the `grafana-alerts` tool crate (webhook route + producer), the shared `IngressStore`, the coordinator and grafana investigator agents. Webhook receiver is part of the runner — no separate ingress pod. Agents are deployed packages, not invocations.
- **Slack notify agent**: `agents/slack-notify/` deployed alongside the coordinator. Reachable via A2A inside any active `context_id`. Posts via `support/slack_notify`.
- **Failure harness**: deployed daemon. Schedules or accepts on-demand injections. Writes ledger + incident/trace annotations.
- **`checkout-api` / `payments-api` / k6**: deployed services with continuous baseline traffic.

Continuity semantics (already in §Provenance Link):

- Repeated `firing` webhooks for the same Grafana fingerprint reuse the existing `context_id`. The investigation appends; it does not re-fire a fresh one.
- `resolved` webhook reuses the active `context_id`, marks the mapping resolved, and appends a resolution message to the same investigation.
- A new `firing` after a resolved state mints a new `context_id`.

This matters for the demo narration: the audience should see that the system reacts to *the same* incident across firing → progress → resolved without a human re-triggering anything, and that a second incident lands in a fresh investigation.

## Demo Environment

Kubernetes cluster with:

1. **Dummy service pair**
   - `checkout-api`: public service under test.
   - `payments-api`: downstream dependency stub.
   - `checkout-api` calls `payments-api` so dependency failures have real evidence.
   - Both services emit Prometheus metrics.
   - `checkout-api` emits structured JSON logs to stdout for Loki ingestion and synthetic span-like records for injected incidents (spans mirrored into Grafana annotations; traces still synthetic).

2. **Synthetic load generator**
   - Required.
   - Uses `grafana/k6` image with a ConfigMap-mounted script.
   - Constant-arrival-rate executor at 50 RPS minimum so histogram p95 buckets actually shift within the alert window.
   - Stable baseline traffic with low error/latency.

3. **Failure harness daemon**
   - **Sole writer of Grafana annotations** (incident window, synthetic trace/span evidence records, resolved markers). Owns schedules, on-demand injections, ground-truth ledger, and cleanup. The `grafana-alerts` tool never writes annotations — keeps Grafana credentials and write surface in one place.
   - Calls service admin endpoints to activate/stop modes.
   - Writes annotations directly via Grafana HTTP API (`POST /api/annotations`). Agents do not get annotation-write tools — read-only `get_annotations` is the contract for windows/traces.
   - Stores ledger in SQLite on a PVC.

4. **Loki + log shipper** (vendored manifests, version-pinned)
   - Loki stores real structured application logs from pod stdout.
   - A lightweight log shipper (Grafana Alloy preferred; promtail acceptable if easier) tails Kubernetes pod logs and pushes to Loki.
   - Logs are correlated by `service`, alert time window, route/status fields, and message keywords — not by demo-only `incident_id`.

5. **Grafana + Prometheus datasource config** (vendored manifests, version-pinned)
   - Prometheus scrapes services.
   - Grafana dashboards show live service health.
   - Grafana has Prometheus and Loki datasources provisioned.
   - Grafana alert rules detect injected incidents.
   - Grafana annotations carry incident windows plus synthetic trace evidence (see §Annotation Payload Schema). Logs live in Loki, not annotations.
   - Grafana webhook posts alerts to a route served by the Agentium runner (provided by the `grafana-alerts` tool crate — see §Grafana Alerts Integration). No standalone ingress service.

6. **`grafana-alerts` tool crate (in-runner)**
   - Lives at `crates/tools/grafana-alerts`, modeled on `crates/tools/slack`.
   - Declares `event_sources = ["grafana"]` in tool metadata and registers a `GrafanaAlertEventProducer` via the existing inventory pattern.
   - Webhook route runs inside the runner (or as a runner-managed handler) and persists incoming payloads via the runner's existing `IngressStore` — no bespoke inbox table.
   - Owns the only legitimately new persistence: a small mapping table for active alert `fingerprint`/`groupKey` → Agentium `context_id` with firing/resolved reuse semantics (see §Provenance Link).
   - `EventProducer` drains `IngressStore` on the runner poll loop and emits `grafana.alert.v1` events with `context_id` + `message_id` already resolved against the mapping table.
   - Coordinator subscribes via manifest `discovery.subscriptions` matching `schema_versions=["grafana.alert.v1"]` and `source_kinds=["grafana"]`; existing host dispatch path delivers to `onDispatch` with no new wiring.

7. **Agentium-OS runtime**
   - Runner deployed in cluster.
   - Three agents total — see §Agent Roles:
     - Observability coordinator (also synthesizes final report).
     - Grafana investigator (metrics via Prometheus, logs via Loki/LogQL, synthetic traces via annotations).
     - Slack notifier (`agents/slack-notify/`, new write-only agent backed by `support/slack_notify`).
   - All three share the same Agentium `context_id` per incident so they collaborate in-context.

## Failure Harness

The harness makes the live system reproducible.

### Owner

Use a separate `failure-harness` deployment, not in-process service-only state.

```txt
POST failure-harness/admin/failure-mode
  -> harness writes ledger start row
  -> harness calls checkout-api/admin/failure-mode
  -> harness posts Grafana annotation
  -> harness waits duration or stop command
  -> harness calls checkout-api/admin/failure-mode healthy
  -> harness finalizes ledger ended_at
```

### Modes

**For the first recording, only `latency_spike` is implemented.** `dependency_timeout` and `brief_offline` move to nice-to-have. One failure mode, one alert, one investigator path keeps the demo small and the harness code minimal.

#### 1. Scheduled mode (nice-to-have)

Used for human demo browsing once the core path is recorded.

Examples (deferred):

```txt
HH:15 latency_spike for 5m
HH:35 dependency_timeout for 5m
HH:50 brief_offline for 2m
```

If enabled later:

- `pause_schedule` flag to avoid collisions with manual demos.
- Schedule visible in runbook.
- Scheduled injections disabled in CI.

Not required for the first recording.

#### 2. On-demand mode

Used for operator demos and deterministic E2E evaluation.

Example:

```bash
POST /admin/failure-mode
{
  "mode": "latency_spike",
  "duration_seconds": 300,
  "latency_ms_p95": 1800,
  "error_rate": 0.02,
  "incident_id": "demo-latency-001"
}
```

Early stop / cleanup:

```bash
POST /admin/failure-mode/demo-latency-001/stop
POST /admin/reset-active
```

### Ground-Truth Ledger

Ground truth is produced by the harness, not by agent prompts.

Storage:

- SQLite database on PVC.
- API access for CI and debugging:
  - `GET /admin/ledger`
  - `GET /admin/ledger/{incident_id}`
  - `POST /admin/reset-ledger`

Example row:

```json
{
  "incident_id": "demo-latency-001",
  "service": "checkout-api",
  "dependency": "payments-api",
  "mode": "latency_spike",
  "started_at": "2026-05-21T12:15:00Z",
  "ended_at": "2026-05-21T12:20:00Z",
  "expected_evidence": [
    {
      "kind": "metric",
      "name": "p95_latency",
      "required_query_regex": "histogram_quantile\\(0\\.95.*demo_service_request_duration_seconds_bucket",
      "required_labels": {"service": "checkout-api"},
      "expected_value_min": 0.75,
      "expected_value_unit": "seconds",
      "time_overlap_required": true
    },
    {
      "kind": "log",
      "name": "dependency_timeout_log",
      "required_substrings": ["dependency timeout", "payments-api"],
      "required_labels": {"service": "checkout-api"},
      "min_count": 1,
      "time_overlap_required": true
    },
    {
      "kind": "trace",
      "name": "slow_payment_span",
      "required_substrings": ["POST /payments/authorize", "slow dependency span"],
      "required_labels": {"service": "checkout-api", "dependency": "payments-api"},
      "min_count": 1,
      "time_overlap_required": true
    }
  ]
}
```

Rules:

- Agents never read the ledger.
- E2E evaluation reads the ledger to verify cited evidence.
- Reviewers can inspect ledger for expected behavior.
- Ledger can be reset independently from telemetry retention.

### Time Overlap Window

`time_overlap_required: true` means the evidence timestamp must fall within:

```txt
[started_at - 30s, ended_at + 90s]
```

Asymmetric on purpose: 30s leading margin absorbs clock skew between harness and Prometheus; 90s trailing margin absorbs scrape/eval lag (default scrape interval 15s, Grafana evaluation interval up to 1m). One rule for all evidence kinds keeps the eval simple.

## Annotation Payload Schema

Grafana annotations carry incident windows and synthetic span-like evidence only. Real logs live in Loki and are queried with LogQL through Grafana. Agents read annotations through `mcp/grafana/get_annotations`; the harness writes them through the Grafana HTTP API. Trace/span annotations are not real Tempo traces — the disclaimer must appear in narration and runbook.

### Tags

Tags drive agent filtering. Every annotation carries at minimum:

```txt
agentium-demo
incident=<incident_id>
service=<service>
kind=<window|trace>
```

- `kind=window` — one per incident, spans `started_at..ended_at` using Grafana annotation `time=started_at_ms` and `timeEnd=ended_at_ms`.
- `kind=trace` — N per incident, one per representative synthetic trace/span.
- `kind=window,status=resolved` — close marker at `time=ended_at_ms` when the harness stops the injection or Grafana sends a resolved webhook.

Report bodies are not Grafana annotations. Final report text lives in Agentium provenance as synthesizer/coordinator LLM output under the investigation `context_id`.

### Text payload

Text is a compact JSON blob (≤ 1 KB suggested per annotation). For `kind=trace`:

```json
{
  "incident_id": "demo-latency-001",
  "service": "checkout-api",
  "kind": "trace",
  "trace_id": "9f2c…",
  "span_id": "ab12…",
  "parent_span_id": "00…",
  "operation": "POST /payments/authorize",
  "dependency": "payments-api",
  "duration_ms": 1740,
  "status": "error",
  "note": "slow dependency span"
}
```

No OTLP/Tempo backend involved — trace records live as structured annotations only.

### CI Determinism

CI uses on-demand mode only. For full rehearsal, CI can wait for Grafana alert evaluation. For faster deterministic tests, CI may synthesize the Grafana webhook payload from the harness ledger and POST it directly to the runner's `grafana-alerts` webhook route, bypassing Grafana evaluation interval flake while still exercising the ingestion/dispatch/investigation path.

```txt
full rehearsal:
  harness injects failure
    -> wait for Prometheus scrape + Grafana alert
    -> receive/dispatch grafana.alert.v1
    -> run Agentium investigation
    -> assert evidence against ledger

fast deterministic eval:
  harness injects failure
    -> wait for Prometheus scrape only
    -> synthesize Grafana webhook payload from ledger
    -> POST directly to runner's grafana-alerts webhook route
    -> run Agentium investigation
    -> assert evidence against ledger
```

## Alert/Event Flow

```txt
checkout-api emits bad metrics, real logs, and synthetic trace evidence
  -> Prometheus scrapes metrics
  -> log shipper pushes structured pod stdout logs to Loki
  -> Grafana alert fires on real metrics
  -> Grafana webhook sends alert payload
  -> grafana-alerts tool webhook (in-runner) receives payload
  -> ingress maps active alert fingerprint/groupKey to Agentium context_id
  -> GrafanaAlertEventProducer emits a ProducedEvent (grafana.alert.v1) with context_id + message_id
  -> host subscription matching dispatches the event to the coordinator's onDispatch
  -> observability coordinator receives event via subscription
  -> dashboard stream shows incident event and live investigation progress
  -> coordinator delegates to grafana investigator
  -> grafana investigator gathers metrics + Loki log evidence + trace annotation evidence
  -> coordinator synthesizes final report (no separate synthesizer agent)
  -> coordinator hands summary + dashboard URL to slack-notify agent via A2A
       in the shared context_id
  -> slack-notify calls support/slack_notify to post in configured channel
  -> final report LLM output is stored in provenance
  -> operator views full investigation at ${AGENTIUM_UI_BASE_URL}/?view=dashboard&contextId={context_id}
```

Raw API fallback for CI/debugging:

```txt
GET /contexts/{context_id}/conversation-history
GET /contexts/{context_id}/conversation-history/stream
```

## Agent Roles

Three agents total for the demo. All share the same Agentium `context_id` per incident so they collaborate in-context through A2A messages/artifacts projected via `baml-rt-conversation`.

### Observability Coordinator Agent

Owns broad alert subscription. Also acts as report synthesizer in its final LLM step (no separate synthesizer agent for this demo).

Responsibilities:

- Implement `onDispatch(request: HostDispatchRequest)`; event subscriptions invoke `onDispatch`, not chat `run`.
- Receive `grafana.alert.v1` events.
- Parse severity, alert name, affected service, time window, dashboard/panel links.
- Normalize incident context and delegate to the grafana investigator.
- Emit progress/intermediate status messages so the dashboard can show live investigation progress.
- Synthesize final report: merge investigator evidence into impact, likely cause, confidence, open questions, next actions, and citations. Provenance stores the LLM output automatically.
- Hand summary + dashboard URL to `agents/slack-notify/` via A2A inside the shared `context_id` for channel post. Do not call `support/slack_notify` directly — that capability belongs to slack-notify.
- Do not rely on `ctx.tags["conversation_history"]`; investigator outputs must flow as A2A messages/artifacts projected through `baml-rt-conversation`.
- Demo may run the full investigation synchronously inside `onDispatch`; acceptable for a one-alert demo, but production should decouple fast ack from long-running investigation.

Dedup by fingerprint/group key is deferred to nice-to-have, but context continuity is required: repeated firing/resolved events for the same Grafana fingerprint/groupKey must reuse the same Agentium `context_id`.

Manifest subscription sketch:

```json
{
  "discovery": {
    "subscriptions": [
      {
        "schema_versions": ["grafana.alert.v1"],
        "source_kinds": ["grafana"],
        "source_keys": ["grafana:local"]
      }
    ]
  }
}
```

`source_keys` narrowing is cheap and avoids accidental cross-talk if a second Grafana instance is ever added.

### Grafana Investigator Agent

One agent covers metrics, logs, and traces. Same Grafana MCP server, same context window, separate datasource queries — splitting into three agents was cosmetic agency. Annotation payloads are ≤1KB each (see §Annotation Payload Schema), Loki/Prometheus responses over a 5-minute window are small, so flooding the agent context is not a real risk at demo scale.

Tools (core):

- `mcp/grafana/list_datasources` — find Prometheus and Loki UIDs once.
- `mcp/grafana/query_prometheus` — PromQL for p95 latency, error rate, request rate, `up`; baseline vs incident window.
- Grafana Loki datasource query / LogQL tool — query real logs for the affected service over the alert window. If the MCP server exposes a generic datasource query instead of `query_loki`, use that.
- `mcp/grafana/get_annotations` — retrieve incident window and trace evidence:
  - `tags=kind=window` + `incident=<incident_id>` → incident bounds/resolution markers.
  - `tags=kind=trace` + `incident=<incident_id>` → synthetic span evidence.

Tools (optional polish):

- `mcp/grafana/search_dashboards`
- `mcp/grafana/get_dashboard_summary`

Manifest note: package must include `mcp/grafana/get_annotations`, `mcp/grafana/query_prometheus`, and whichever Grafana MCP operation can query Loki (prefer `query_loki` if present, otherwise generic datasource query). The current `examples/agents/grafana-mcp-agent` read-only starter must be extended before it can play this role.

Responsibilities:

- Identify Prometheus and Loki datasources.
- Emit progress/status messages for dashboard live view.
- Query PromQL around the alert timestamp; compare baseline vs incident window.
- Query Loki around the alert timestamp with bounded LogQL, e.g. `{service="checkout-api"} |= "payments-api"` or `{app="checkout-api"} | json | route="/api/checkout" | status >= 500`; identify repeated errors and dependency timeout messages. Do not require `incident_id` in application logs.
- Retrieve synthetic span-like annotations (bounded query: `limit≤20`, time bound = alert window ± overlap margin); identify the slow span and dependency (`payments-api`).
- Return structured findings (metric query text/labels/values, representative log lines, span evidence) with archive refs for coordinator synthesis.

Investigator must apply `limit` and time-bound filters on annotation and Loki queries to defend against context drift in a long-lived runner where data grows over time.

Future extension: replace synthetic span annotations with Tempo MCP for traces when that backend ships. Split back into per-signal agents if/when scope warrants.

### Slack Notifier Agent (`agents/slack-notify/`)

**New agent, not a reuse of `agents/slack-agent/`.** The existing `agents/slack-agent/` is read-only (manifest description: "Read-only Slack assistant"; tools are `support/slack` + `system/*`; no write tool, no `onDispatch`) and cannot post. It remains in the repo for a future Slack-as-input / human follow-up role and is out of scope for this demo.

`agents/slack-notify/` is a small write-only agent built for the demo:

Tools:

- `support/slack_notify` — new write tool, see below.
- `system/internal_a2a` if needed for response acks.

Configuration:

- `SLACK_NOTIFY_CHANNEL_ID` env var on the runner. **Channel ID (`C…`-shaped), not a name** — see the tool spec below. If a name is supplied for convenience, the tool resolves it to an ID once at startup.
- Slack bot token resolved via the standard secret resolver chain.

Responsibilities:

- Receive synthesized summary + dashboard URL from coordinator via A2A in the shared `context_id`.
- Format a compact message (incident summary, severity, service, dashboard URL, optional resolved update).
- Call `support/slack_notify` once per incident message.
- Demonstrates multi-agent same-context collaboration: coordinator and slack-notify both operate inside the same Agentium investigation context.

Final report body still lives in Agentium provenance; the Slack message is a pointer + summary, not the canonical record.

#### `support/slack_notify` tool

New write tool crate at `crates/tools/slack-notify` (or a write surface added to `crates/tools/slack`). One operation: post a message to a configured channel via Slack `chat.postMessage`.

Tool registry name: `support/slack_notify` (underscore in the operation segment matches existing tool naming such as `system/discover_agents`, `system/internal_a2a`). If the registry instead enforces hyphens in the operation segment, use `support/slack-notify` — pick one and use it consistently across the tool crate registration, manifest, codegen, and provenance.

**LLM-visible input** (strict; `serde(deny_unknown_fields)`):

```json
{
  "text": "...",
  "context_id": "..."
}
```

- No `channel` field. Any `channel` key in the model's output is rejected at deserialize time — the LLM cannot redirect posts to a different channel.
- No `thread_key` field. The tool derives Slack threading internally from `context_id` (in-memory map for demo) so firing, progress, and resolved updates for one incident land in one Slack thread. The LLM has zero control over threading.

**Configuration**:

- `SLACK_NOTIFY_CHANNEL_ID` env var. **Runbook requires a Slack channel ID** (`C0123456789`-shaped). A name-to-ID resolution path exists as a best-effort developer convenience only: if a `#name` is supplied, the tool resolves it once at startup via `conversations.list`, caches the result, and refuses to start if resolution fails. Per-call lookup is never performed. Production / recording config should always pass the channel ID directly.
- Bot token from secret resolver, never from agent input.
- Tool-call archives in provenance give full audit (who/when/what posted).

**Outbound is per-tool by design.** The host's event delivery substrate (subscriptions, producers, `IngressStore`, `onDispatch`) is **inbound only**. There is no symmetric outbound channel in the runtime, and adding one is not on the platform roadmap. Outbound writes therefore land in write tools like `support/slack_notify` invoked normally through the session FSM. The Slack notify path is the demo's only outbound surface.

## Provenance Link and Investigation Identity

Runner/API owns the canonical provenance URL. Agents must not invent UI URLs.

Global investigation identity is **Agentium `context_id`**, not Grafana alert ID and not A2A `task_id`.

- Grafana alert identifiers (`groupKey`, `fingerprint`) identify the external alert.
- Prometheus labels, annotation tags, `incident_id`, timestamps, and trace IDs identify service telemetry.
- Agentium `context_id` identifies the investigation/conversation created by the runner.
- A2A `task_id` is per turn/per agent and useful for drill-down only; it is not the global report key.

The `grafana-alerts` tool crate owns the mapping:

```txt
(grafana groupKey/fingerprint) -> Agentium context_id
```

Storage:

- SQLite database (or shared persistence used by the runner) owned by the `grafana-alerts` tool crate. Not a separate pod.
- Mapping table tracks `fingerprint`, `group_key`, `context_id`, `status`, `active_since`, `resolved_at`, and `updated_at`.

Reuse semantics:

- First `firing` for an inactive/new fingerprint creates a new `context_id`.
- Repeated `firing` webhooks while active reuse the existing `context_id`.
- `resolved` webhook reuses the active `context_id`, marks mapping inactive/resolved, and appends resolution to the same investigation.
- First `firing` after a resolved state creates a new `context_id` even if fingerprint/groupKey is identical.
- Resolved mappings may be retained for 24h for debugging, but are not reused.

Runtime requirement (supported by current dispatch path): produced events must include **both** `context_id` and `message_id`; otherwise dispatch falls back to synthetic scope and provenance continuity is lost. Subscriptions are only applied on the `EventProducer` path; a direct `POST /agents/{pkg}/{instance}/dispatch` prototype would bypass subscription matching and is not the target product path.

Recommended message ID:

```txt
message_id = grafana:<fingerprint>:<status>:<startsAt>
```

Repeated firing webhooks for the same active alert naturally share the same `message_id`; suppressing duplicates is still nice-to-have, but continuity does not depend on dedup.

The runbook and chart pre-fill the base URL:

```txt
AGENTIUM_UI_BASE_URL=http://localhost:18080   # default for demo, port-forward to runner
operator dashboard URL = ${AGENTIUM_UI_BASE_URL}/?view=dashboard&contextId={context_id}
raw transcript API = ${AGENTIUM_UI_BASE_URL}/contexts/{context_id}/conversation-history
```

`/contexts/{context_id}/conversation-history` exists today as the raw API fallback. The web dashboard currently uses `?view=dashboard&contextId=...`; verify the exact route in the target branch before recording the runbook.

## Report Retrieval

Every LLM output lands in Agentium provenance, so the canonical final report is retrieved from the investigation context. The demo adds Slack as a human-facing notification sink — summary + dashboard URL only, not the canonical record.

Operator paths (in fallback order — the demo must work even if the dashboard route is broken):

1. **Slack channel** — `agents/slack-notify/` posts a summary + dashboard URL on each incident via `support/slack_notify`. Primary human-in-the-loop entry point. Works regardless of dashboard status.
2. **Raw provenance APIs** — guaranteed fallback for the recording:
   - `GET /contexts/{context_id}/conversation-history` — ordered transcript.
   - `GET /provenance/llm-calls?context_id={context_id}` — investigator and coordinator LLM outputs incl. final report.
   - `GET /provenance/tool-calls?context_id={context_id}` — MCP evidence archives.

## Grafana Alerts Integration

The runner already provides the full host-to-agent event delivery substrate (see `docs/host-to-agent-event-delivery.md`): the `EventProducer` trait, inventory-based producer registration, a shared `IngressStore`, the generic `host.source-records.v1` envelope, subscription matching by `schema_versions` + `source_kinds`, and the `POST /agents/{pkg}/{inst}/dispatch` delivery endpoint. `support/slack` is the reference production tool wired through this path.

`grafana-alerts` plugs into that substrate exactly the way `support/slack` does — no standalone ingress service, no bespoke inbox table, no separate deployment.

Shape:

```txt
crates/tools/grafana-alerts
  -> tool metadata declares event_sources = ["grafana"]
  -> inventory registers GrafanaAlertEventProducer via EventProducerProvider
  -> webhook handler (runner-served) receives Grafana payload
       and enqueues an IngressItem on the shared IngressStore
  -> mapping table (tool-local, small) resolves
       fingerprint/groupKey -> Agentium context_id with firing/resolved reuse
  -> GrafanaAlertEventProducer drains IngressStore on the runner poll loop
       and emits grafana.alert.v1 ProducedEvent with context_id + message_id
  -> host subscription matching delivers to the coordinator's onDispatch
```

What this means concretely:

- **No new deployment.** The webhook lives in the runner (or a runner-managed sidecar handler), not as a separate `grafana-alerts-ingress` pod.
- **No new inbox.** `IngressStore` is reused. `SlackInboxEventProducer` is the working reference (`crates/tools/slack/src/producer.rs`); the Grafana producer is the same pattern.
- **No new dispatch wiring.** The producer emits `ProducedEvent`s; the runner's existing subscription-matching path turns each event into an `AgentDispatchRequest` for every matching agent and delivers via `POST /agents/{pkg}/{inst}/dispatch`. The runner enforces `context_id` + `message_id` propagation on the dispatch envelope. The producer does not know or care who subscribes — fan-out is the host's job.
- **Only legitimately new persistence**: the alert-identity → investigation-identity mapping table owned by the tool crate. Small. Carries firing/resolved reuse logic from §Provenance Link.

Important distinctions:

- Agents do not poll alerts.
- Grafana webhook triggers ingestion via the tool-crate webhook route.
- The host's existing producer/dispatch path delivers events to subscribed agents.
- Grafana MCP is used **after** trigger for investigation/enrichment (separate read-only tool surface).

Event shape:

```json
{
  "schema_version": "grafana.alert.v1",
  "source_kind": "grafana",
  "source_key": "grafana:local",
  "context_id": "<agentium-context-id-minted-by-ingress>",
  "message_id": "grafana:<fingerprint>:<status>:<startsAt>",
  "messages": [
    {
      "status": "firing",
      "receiver": "agentium-webhook",
      "groupKey": "...",
      "alerts": [
        {
          "status": "firing",
          "labels": {
            "alertname": "HighLatency",
            "service": "checkout-api",
            "severity": "warning"
          },
          "annotations": {
            "summary": "checkout-api p95 latency is high",
            "description": "p95 latency exceeded threshold for 5m"
          },
          "startsAt": "...",
          "endsAt": "...",
          "fingerprint": "...",
          "dashboardURL": "...",
          "panelURL": "..."
        }
      ]
    }
  ]
}
```

### 2. Show live baseline

- Prometheus targets healthy.
- Agentium agents registered/discoverable.
- Coordinator subscribed to `grafana.alert.v1`.
- Harness ledger empty or shows prior scheduled events.

### 3. Inject latency spike on demand

Run:

```bash
kubectl exec deploy/failure-harness -- \
  curl -X POST localhost:8080/admin/failure-mode \
  -H 'content-type: application/json' \
  -d '{"mode":"latency_spike","duration_seconds":300,"latency_ms_p95":1800,"incident_id":"demo-latency-001"}'
```

Harness writes:

- ground-truth ledger row
- Grafana annotations: `kind=window` for incident and `kind=trace` per representative synthetic span record
- Loki logs: structured stdout records from checkout-api/payments-api during the incident window
- active mode state in checkout-api

### 4. Grafana alert fires

- Grafana evaluates alert on real metrics.
- Webhook posts to the runner-served `grafana-alerts` webhook route.
- `grafana-alerts` producer emits `ProducedEvent`; host subscription matching dispatches it to the coordinator.
- Coordinator receives dispatch.

### 5. Agent investigation

Presenter opens the dashboard before or during the alert:

```txt
${AGENTIUM_UI_BASE_URL}/?view=dashboard&contextId=<context_id>
```

The dashboard should show the incident event, investigator activity, MCP calls, and final report as the conversation/provenance stream updates. If the investigator runs through `system/internal_a2a`, its detailed work may live in a linked child context; the dashboard must at least show the parent context's internal_a2a calls and returned investigator summary, with linked child-context drilldown preferred.

Coordinator delegates to grafana investigator (single agent, all three evidence kinds):

```txt
Grafana investigator:
  - PromQL: latency/error/request rate around incident window
  - Loki LogQL: dependency timeout messages from checkout-api/payments-api
  - annotations kind=trace: slow payments-api span
```

Coordinator then synthesizes the final report (no separate synthesizer agent) and hands the summary + dashboard URL to `agents/slack-notify/` via A2A in the shared `context_id`. slack-notify calls `support/slack_notify` to post the message in the configured channel.

Example PromQL:

```promql
histogram_quantile(0.95, sum(rate(demo_service_request_duration_seconds_bucket{service="checkout-api"}[2m])) by (le))
```

```promql
sum(rate(demo_service_requests_total{service="checkout-api",status=~"5.."}[2m]))
```

```promql
up{job="checkout-api"}
```

### 6. Operator retrieves the report

Retrieval path:

- **Dashboard** — `${AGENTIUM_UI_BASE_URL}/?view=dashboard&contextId={context_id}` shows the incident event, investigator outputs, MCP/tool evidence drilldown, and final synthesizer message.
- **Raw API for CI/debug** — `GET /contexts/{context_id}/conversation-history` returns ordered transcript; `/provenance/tool-calls?context_id={context_id}` and `/provenance/llm-calls?context_id={context_id}` expose structured audit data.

The operator sees this report shape:

```txt
🚨 Grafana Alert: HighLatency firing
Service: checkout-api
Severity: warning
Started: 2026-xx-xxTxx:xx:xxZ

Summary:
- p95 latency rose from ~120ms baseline to ~1.8s during the alert window.
- Error rate stayed low, so this appears to be degradation, not outage.
- Service remained up during the event.
- Log evidence shows dependency timeout warnings for payments-api.
- Trace evidence points to slow POST /payments/authorize spans.

Evidence:
- Prometheus p95 latency query: 1.8s
- Request rate stable: ~N rps
- up == 1
- Structured log: "dependency timeout" for payments-api (annotation id <n>)
- Synthetic trace span: POST /payments/authorize slow dependency span (annotation id <n>)

Links:
- Grafana dashboard: <url>
- Panel: <url>
- Transcript/provenance: ${AGENTIUM_UI_BASE_URL}/?view=dashboard&contextId=<context_id>

Suggested next actions:
1. Check payments-api dependency latency.
2. Confirm whether this was expected demo injection.
3. Watch alert resolution in next 5 minutes.
```

The final report is not written to Grafana. It is already stored as Agentium provenance under the investigation `context_id`.

### 7. Alert resolves

- Harness duration ends or operator calls the stop endpoint.
- Harness returns service to healthy.
- Grafana sends resolved webhook.
- `grafana-alerts` tool reuses the same active `context_id` for the resolved update, marks the mapping resolved, and stops future reuse.
- **Failure harness writes the `kind=window,status=resolved` Grafana annotation** at `time=ended_at_ms`. The `grafana-alerts` tool only ingests alert webhooks and maps `context_id`; it never writes Grafana annotations. Single annotation writer = harness.
- Coordinator appends a resolved update to the same investigation provenance context:

```txt
✅ HighLatency resolved for checkout-api after 5m.
Latency returned to baseline (~120ms p95).
```

### 8. E2E eval checks ledger

#513-style eval:

```txt
read ledger incident_id=demo-latency-001
read context_id from grafana-alerts mapping/dispatch ack
read /provenance/tool-calls?context_id=...
read /provenance/llm-calls?context_id=...
read final report citations from /contexts/{context_id}/conversation-history or /provenance/llm-calls?context_id=...
assert expected metric/log/trace evidence was retrieved and cited
```

Citation matching rules:

- Metric evidence: tool-call archive contains PromQL matching `required_query_regex`, required labels, time overlap, and value threshold.
- Log evidence: evidence archive/report citation contains required substrings, labels, and incident-window overlap.
- Trace evidence: evidence archive/report citation contains required operation/dependency substrings, labels, and incident-window overlap.
- Final report must cite archive/provenance refs for each required evidence kind.

## Why This Architecture

Static replay fixtures are predictable but less convincing. Live deterministic workload gives both realism and testability.

Wins over record/replay:

- No snapshot volumes to ship.
- Real Prometheus scrape/evaluation path.
- Grafana MCP queries hit live datasource.
- Demo users can explore history between scripted runs.
- One still-small stack: Grafana + Prometheus + Loki.

Clean separation:

```txt
Dummy services = realistic workload + evidence generation
Failure harness = deterministic incident windows + ground truth + Grafana annotations
Grafana       = detection, visualization, single user-visible surface (incl. evidence)
Prometheus    = metrics store
Loki          = logs store
Grafana MCP   = metrics + Loki/log + annotation enrichment API (read-only for agents)
Agentium producer = alert event ingestion + Grafana alert -> context_id mapping
Coordinator   = routing + synthesis; final report is visible through dashboard/provenance
Dashboard = operator-facing provenance drilldown by context_id
Provenance API = CI/eval raw transcript and structured evidence by context_id
```

## Demo Scope

This is a demonstration project, not a product MVP. Scope below reflects what is required for the first recording vs. what can be added later.

Must-have for first recording:

- Helm chart and vendored, version-pinned Grafana + Prometheus + Loki + log shipper manifests under `demo/ford-observability/helm/`.
- `just demo-observability-images` recipe that builds and loads/pushes service images.
- `just demo-observability-e2e` recipe — first cut runs the smoke path (install → inject → wait → fetch report + ledger). The ledger-assertion stage is nice-to-have and lands after the first recording (see §Demo Scope).
- README/runbook with install, inject, reset, troubleshoot, and expected-output steps, including the **honest framing** disclaimer.
- Grafana + Prometheus + Loki for the observability backend.
- `checkout-api` and `payments-api` services (Rust, separate workspace under `demo/ford-observability/`).
- Required `k6-load-generator` at constant 50 RPS minimum.
- Failure harness daemon with on-demand `POST /admin/failure-mode` and matching stop/reset endpoints. **One failure mode only for first recording: `latency_spike`.**
- SQLite ground-truth ledger with the time-overlap rule from §Time Overlap Window. **Ledger writes are required; the E2E assertion runner is soft-deferred (see nice-to-have).**
- Metrics evidence via `mcp/grafana/query_prometheus`.
- Real log evidence via Loki/LogQL queried through Grafana, bounded by alert time window and filtered by `service` plus route/status/message fields. Application logs must not rely on a demo-only `incident_id`.
- Synthetic span-like evidence via Grafana annotations (`kind=trace`) read by `mcp/grafana/get_annotations` with `limit` and time-bound filter.
- Grafana dashboard + **one alert (`HighLatency`)**.
- `kind=window` annotation for injected windows and `kind=window,status=resolved` annotation on close; report body stored in Agentium provenance, not Grafana.
- Grafana webhook to runner-served `grafana-alerts` webhook route.
- `grafana-alerts` tool crate (in `crates/tools/grafana-alerts`, modeled on `crates/tools/slack`) with: webhook route served by the runner, `IngressStore`-backed intake, small SQLite mapping table for active alert fingerprint/groupKey → `context_id`, and `GrafanaAlertEventProducer` registered via inventory.
- `grafana.alert.v1` event dispatch to the coordinator with both `context_id` and `message_id`.
- Coordinator agent implements `onDispatch`; chat-only agents are not valid event subscribers. Coordinator caps investigation at ~60s wall clock and emits progress on each tool call.
- Three agents total: coordinator (also synthesizes), grafana investigator (metrics + Loki logs + trace annotations), `agents/slack-notify/` (new write-only agent backed by `support/slack_notify`). All share the same `context_id` per incident.
- New `support/slack_notify` write tool — one operation (post to a configured channel via `chat.postMessage`). Strict input (`text` + `context_id`, `deny_unknown_fields`; LLM cannot set channel or thread). Channel from `SLACK_NOTIFY_CHANNEL_ID` env var, **must be Slack channel ID** (`C…`); name fallback resolved once at startup. Threading derived per `context_id`. Bot token from secret resolver. Existing `agents/slack-agent/` is read-only and is **not** the notifier.
- Slack post on each incident: short summary + dashboard URL. Primary human-facing surface.
- Provenance API fallback (`/contexts/{id}/conversation-history`, `/provenance/llm-calls`, `/provenance/tool-calls`) verified working for recording even if the dashboard route is broken.
- Final report with cited evidence and the `${AGENTIUM_UI_BASE_URL}/?view=dashboard&contextId={context_id}` provenance/dashboard link (route verified in target branch).
- Local Kubernetes target: **k3d** (matches the repo's existing e2e harness via `just e2e-k8s`). kind also works but is not the default.
- Recorded demo + written demo script under `docs/demos/ford-grafana/`.
- CI/eval environment pins `BAML_TEST_MODEL=x-ai/grok-4.3` by default; local runs may override.

Nice-to-have (after the first recording lands):

- E2E assertion runner that reads the ledger and asserts metric/log/trace evidence was retrieved and cited. (Ledger writes stay must-have; the assertion harness can land later.)
- Web chat UI (`web/`) attached to investigation `context_id` for human follow-up questions to the coordinator inside the same session.
- Scheduled injection mode.
- Additional failure modes: `dependency_timeout`, `brief_offline`.
- Resolved-alert report update beyond the minimal resolved provenance message.
- Multiple dummy services.
- Deduplication by fingerprint/groupKey.
- Severity/team-based routing.

Out of scope for first demo:

- MS Teams / generic webhook delivery (Slack is in scope via new `agents/slack-notify/` + `support/slack_notify`; existing `agents/slack-agent/` is read-only and not the notifier).
- Coordinator chat retrieval of past reports without a provenance-read tool or existing-context chat UX.
- Tempo.
- Mimir.
- Real Ford data.
- Real FireHydrant API integration.
- Full incident lifecycle management.
- Real PagerDuty/Opsgenie/OnCall integration.
- Multi-cluster production hardening.
- Automated remediation.
- General-purpose context culling.
- Webhook signing/HMAC verification.
